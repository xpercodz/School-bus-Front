# Audit-log storage for this stack (Firestore + Cloud Run + offline client writes)

**Question.** A director-readable audit trail of "major behaviours" must be tamper-evident and not forgeable by the browser client that is being audited. How should it be stored and written in *this* stack — React 19 + Vite SPA on Firebase Hosting, Hono on Node 22 on Cloud Run (`/v1/**` rewritten same-origin), Firestore native mode, Firebase Auth for director/operator and 6-digit codes for drivers, with attendance/roster writes made **directly by the browser** through the Firestore client SDK and its persistent local cache?

**Versions in force.** Firebase JS SDK v12 (`firebase@^12.18.0` in `package.json`; the v9+ modular API is what v12 ships, so `serverTimestamp()`, `runTransaction()` and `persistentLocalCache()` behave as documented for the modular SDK). Firestore Security Rules v2 (`rules_version = '2'` in `firebase/firestore.rules`).

**Companion note.** `docs/research/2026-02-audit-log-for-directors.md` covers the event schema, the catalogue of "major behaviours" and the reader experience; this note covers storage, the writer, and what each option cannot do.

**Method.** Every claim below was read on the page that owns it; sources fetched 2026-11-11. Google pages reported "Last updated 2026-11-10 UTC" unless noted. Where a claim is **not** stated in the docs I could reach, it is marked **⚠ uncertain** rather than asserted — there are several, and two of them matter for the design (per-document write rate, transaction write cap).

---

## 0. Answer in one paragraph

Rules can make a collection append-only for SDK clients (`create` allowed, `update`/`delete` denied) and can pin a timestamp field to `request.time`, but rules cannot rate-limit, cannot order writes, cannot force an audit entry to exist for a direct write (except inside a transaction via `getAfter()`), and do not apply to the Admin SDK at all. That last point is the whole design: the only writes a browser cannot forge are the ones the browser cannot make. In this stack the trustworthy audit entries must therefore be produced **server-side** — by the existing Hono API (Admin SDK over ADC) for every privileged action, and by a Firestore-triggered Cloud Function (gen 2, with auth context) for the direct roster/attendance writes that must keep working offline. An append-only Firestore collection with `allow read: if <director>; allow write: if false` is then the store; hash-chaining adds detection of edits by someone who *does* hold Admin SDK credentials, but only if the chain head is periodically sealed outside Firestore (locked Cloud Storage object or locked Cloud Logging bucket). Client-written "audit" documents are at best an untrusted inbox of claims, never the director-facing log.

## 1. Firestore Security Rules: append-only, what can be validated, what cannot

### 1.1 Rules are per-operation, so append-only is expressible

- Rules split reads into `get`/`list` and writes into `create`/`update`/`delete`, so creation and mutation can be governed by different conditions ([rules-structure#granular_operations](https://firebase.google.com/docs/firestore/security/rules-structure#granular_operations)). **So what:** `create` can be allowed (or denied) while `update` and `delete` are denied — the literal shape of append-only.
- The docs state `create` applies to "writes to nonexistent documents" and `update` to "writes to existing documents" ([rules-structure#granular_operations](https://firebase.google.com/docs/firestore/security/rules-structure#granular_operations)). **So what:** a `set()` that lands on an existing document ID is an `update` and hits the deny — so the deny cannot be sidestepped by using `set()`.
- Multiple `match` blocks can match one document, and "the access is allowed if any of the conditions is true" ([rules-structure#overlapping_match_statements](https://firebase.google.com/docs/firestore/security/rules-structure#overlapping_match_statements)). **So what:** "append-only" is a property of the **whole ruleset**, not of one block. A later broad `match /schools/{schoolId}/{document=**}` with an allowing `write` silently re-opens the audit collection. `allow write: if false` must be checked against every other match that can reach the path.
- This repo already has the shape: `match /audit/{entryId} { allow read: if isMySchool(schoolId) && isDirector(); allow write: if false; }` ([`firebase/firestore.rules`](../../firebase/firestore.rules)). **So what:** the storage half of the requirement is already satisfied for SDK clients; what is missing is a trustworthy writer and an integrity layer.

### 1.2 `request.resource.data` and `resource.data`

- On write, `request.resource` is the future state of the document, and for an update it is "the pending document state after the operation" ([rules-conditions#data_validation](https://firebase.google.com/docs/firestore/security/rules-conditions#data_validation)). **So what:** rules validate the *resulting* document, which is exactly what you want for an immutable entry: the whole entry is either acceptable or rejected.
- `resource` is the document as it exists now ("the requested document"; `resource.data` is "a map of all of the fields and values stored in the document") ([rules-conditions#data_validation](https://firebase.google.com/docs/firestore/security/rules-conditions#data_validation)). **So what:** `resource.data` is available for `update`/`delete` checks — useful for a "seal" or "chain head" document, and for detecting which fields an update touched.
- The key trap: for updates, `request.resource.data.keys()` "represents the complete document as it would look after the update, and would therefore include fields that the client did not change"; `diff()` + `affectedKeys()` is the documented way to see what actually changed ([rules-fields#restricting_fields_on_update](https://firebase.google.com/docs/firestore/security/rules-fields#restricting_fields_on_update)). **So what:** `hasOnly([...])` on update validates the *whole post-state*, which is right for "an entry can never contain field X", and wrong for "this update may only change field Y" — the latter needs `diff()`.
- On create, `keys().hasOnly([...])` / `hasAll([...])` give an allowlist of fields ([rules-fields#restricting_fields_on_document_creation](https://firebase.google.com/docs/firestore/security/rules-fields#restricting_fields_on_document_creation)). **So what:** an audit entry can be restricted to a fixed field set, so no client (or bug) can smuggle a new field into the schema.

### 1.3 What rules can validate, concretely

- Field set, field types (`is`), field count, and string length: `string.size()` returns the length ([rules.String#size](https://firebase.google.com/docs/reference/rules/rules.String#size)). **So what:** entries can be capped (e.g. reason ≤ 200 chars) so an oversized blob cannot be written into the log.
- String content: `matches(re)` performs a regex match "on the whole string" using Google RE2 syntax ([rules.String#matches](https://firebase.google.com/docs/reference/rules/rules.String#matches)). **So what:** control characters (CR/LF), unexpected characters and non-hex hashes can be rejected at write time — a real defence for §7, and the only content filter that exists in a client-write path.
- Hashes: the rules language exposes `rules.hashing.sha256(bytes_or_string)` (and md5/crc32/crc32c) ([rules.hashing](https://firebase.google.com/docs/reference/rules/rules.hashing)). **So what:** a ruleset *can* verify a single hash link — but only over bytes the rules can produce, which in practice means one string field, not a canonical encoding of a map (**⚠ uncertain**: the docs do not define a canonical serialization, so hashing a whole entry in rules is not something I could confirm).
- Server time: `request.time` can be compared to the written field, with the documented example "Make sure that `myServerTimestampField` was set using a server-side timestamp" ([Request#time](https://firebase.google.com/docs/reference/rules/rules.firestore.Request#time)). **So what:** `request.resource.data.recordedAt == request.time` is the one way to guarantee a *server*-assigned timestamp in a client write.

### 1.4 What rules cannot guarantee

- **Server timestamps are not automatic.** A client can put any `Date`/`Timestamp` in a field; nothing forces `serverTimestamp()`. Only an explicit `request.time` equality check makes the field server-assigned ([Request#time](https://firebase.google.com/docs/reference/rules/rules.firestore.Request#time)). **So what:** without that check, an offline device can back-date an entry, and the ruleset will happily accept it.
- **Ordering.** Rules evaluate one operation at a time ("a boolean expression that determines whether a particular operation should be allowed or denied") ([rules-conditions](https://firebase.google.com/docs/firestore/security/rules-conditions)). There is no primitive for "this entry must come after entry N". **So what:** sequencing has to be established by the writer (a server-assigned counter/hash link) and verified later, never by rules.
- **Dropping fields is all-or-nothing.** "Partial writes are never allowed… You cannot create security rules that accept writes to some fields in your document while rejecting others in the same operation" ([rules-fields#partial_writes_are_never_allowed](https://firebase.google.com/docs/firestore/security/rules-fields#partial_writes_are_never_allowed)). **So what:** a client cannot sneak an extra field in beside valid ones (good), but you also cannot "strip" it — the whole write fails, which must be handled as a real error in the UI, not silently retried.
- **Write rate.** Rules functions "can contain only a single return statement… they cannot execute loops or call external services" ([rules-conditions#custom_functions](https://firebase.google.com/docs/firestore/security/rules-conditions#custom_functions)), and there is no cross-request state. **⚠ uncertain (inference):** there is no rate-limit primitive; the only rate-ish check would be a counter document read and written on every event, which itself becomes a hot document (§6) and burns the access-call budget below.
- **Document access budget.** `get()`/`exists()`/`getAfter()` are capped at 10 per single-document request, 20 for multi-document reads/transactions/batches, with at most 1,000 expressions evaluated per request ([rules-structure#security_rule_limits](https://firebase.google.com/docs/firestore/security/rules-structure#security_rule_limits)). **So what:** rules cannot walk a chain of N links — verification is a job for code, not rules.
- **Reads are whole-document.** "Reads in Rules are performed at the document level… It is impossible using security rules alone to prevent users from reading specific fields within a document"; the docs suggest putting sensitive fields in a separate document ([rules-fields#allowing_read_access_only_for_specific_fields](https://firebase.google.com/docs/firestore/security/rules-fields#allowing_read_access_only_for_specific_fields)). **So what:** every director who can read the audit collection can read *every field* of every entry — so no entry may contain anything that shouldn't be shown to any director (§8).
- **Rules are not filters**, so an audit query cannot be narrowed by rules; the query must satisfy the rule ([rules-conditions#rules_are_not_filters](https://firebase.google.com/docs/firestore/security/rules-conditions#rules_are_not_filters)). **So what:** "director reads their school's log" needs the `schoolId` to be in the path (it already is), not a `where()` clause the rules will reject.
- **`get()` calls cost reads even when the rule rejects the request** ([rules-conditions#access_calls_and_pricing](https://firebase.google.com/docs/firestore/security/rules-conditions#access_calls_and_pricing)). **So what:** a ruleset that reads the profile for every check is the existing, accepted cost, not a free gate.
- **Rules do not apply to the Admin SDK** (§3). **So what:** "append-only" here means "append-only to browsers and SDK clients", not "append-only".

### 1.5 Requiring the audit entry to exist is possible — inside one atomic operation

- `getAfter()` reads a document's state after a transaction or batch completes but before it commits, and the docs show it used to require that related documents are always updated atomically ([transactions#data_validation_for_atomic_operations](https://firebase.google.com/docs/firestore/manage-data/transactions#data_validation_for_atomic_operations)). **So what:** a rule can require "this attendance write is accompanied by this audit entry" — but only if the client uses a transaction/batch and the audit path is fully specified (and it spends the 20-call transaction budget). It forces *existence and atomicity*; it does not make the entry's content true.

## 2. `request.time` and `serverTimestamp()`: who owns the clock

- `request.time` is "when the request was received by the service", and "for Firestore write operations that include server-side timestamps, this time will be equal to the server timestamp" ([Request#time](https://firebase.google.com/docs/reference/rules/rules.firestore.Request#time)). **So what:** there is exactly one clock the client cannot set, and it is exposed to rules for comparison.
- `serverTimestamp()` writes a sentinel that "tracks when the server receives the update" ([add-data#server_timestamp](https://firebase.google.com/docs/firestore/manage-data/add-data#server_timestamp)). **So what:** the resolved value is the backend's receive time, not the device's clock, so it cannot be back-dated — and it also is not the moment the driver tapped.
- Multiple timestamp fields written in one transaction all receive the same server value ([add-data#server_timestamp](https://firebase.google.com/docs/firestore/manage-data/add-data#server_timestamp)). **So what:** one transaction produces one instant, so an entry and its related writes can be ordered internally.
- Yes, a client can *claim* an arbitrary event time: a plain `Timestamp` field is just data. The docs' only mechanism against that is the rules check `request.time == request.resource.data.<field>` ([Request#time](https://firebase.google.com/docs/reference/rules/rules.firestore.Request#time)). **So what:** "when" is trustworthy only for a field that carries that rule; any other time field must be labelled client-asserted.
- Offline changes are synchronised when the device reconnects, and "for multiple changes to the same document, it's last write wins" ([enable-offline](https://firebase.google.com/docs/firestore/manage-data/enable-offline)). **So what:** this is the sharpest consequence in this stack — a tap made in a dead zone at 07:05 is committed at, say, 16:40, so `serverTimestamp()` (and `request.time`) says 16:40 while the school day says 07:05. The audit design needs **two** times, clearly labelled: a server time (trusted, commit time) and a device event time (untrusted, the only record of when it happened).
- OWASP makes the general point: "the event timestamp may be different to the time of logging e.g. server logging where the client application is hosted on remote device that is only periodically or intermittently online" ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). **So what:** this is a known, named log-management problem, not a quirk of Firestore — record both times.
- Version note: in Firebase JS SDK v12 the modular import is `serverTimestamp` from `firebase/firestore` (the repository's dependency), and it remains a sentinel resolved by the backend; no v12-specific behaviour change applies. **So what:** the offline commit-time caveat is a property of the Firestore write path, not of the SDK version.

## 3. Admin SDK vs client SDK: what "server-only" actually means

- "The server client libraries bypass all Cloud Firestore Security Rules and instead authenticate through Google Application Default Credentials. If you're using the server client libraries or the REST or RPC APIs, make sure to set up Identity and Access Management (IAM) for Rules" ([rules-conditions](https://firebase.google.com/docs/firestore/security/rules-conditions)). **So what:** `allow write: if false` is a hard stop for the browser and no obstacle at all for the API — which is precisely the property the audit log needs.
- The Admin SDK's authority is IAM, not rules; the Cloud Run service account's role (e.g. `roles/datastore.user`) is what grants read/write ([Firestore IAM roles](https://cloud.google.com/firestore/docs/security/iam)). **So what:** after this change, the trust boundary for the audit trail is the Cloud Run service account and its key handling — not the ruleset. Anyone who can deploy or run code with that identity can write (or delete) audit entries.
- The same page's note is the only documented statement that "server-side security rules" do not bind server libraries; rules are evaluated for SDK requests ([rules-conditions](https://firebase.google.com/docs/firestore/security/rules-conditions)). **So what:** there is no such thing as a Firestore rule that constrains the API's own writes; the API's code review and IAM are the control.
- App Check does not change this: it attests the app/device, not the server, and is not part of the Admin SDK path ([App Check](https://firebase.google.com/docs/app-check)). **So what:** App Check cannot compensate for a missing server-side write.

## 4. TTL policies for retention

- A TTL policy designates one field as the expiration time for a collection group; docs are typically deleted "within 24 hours after its expiration date", and expiry is not instantaneous — "expired documents continue to appear in queries and lookup requests until the TTL process actually deletes them" ([ttl](https://firebase.google.com/docs/firestore/ttl), [ttl#ttl_deletion](https://firebase.google.com/docs/firestore/ttl#ttl_deletion)). **So what:** TTL is retention, not a deadline: a director can still read an expired entry for up to a day, and a verification job must tolerate that.
- "TTL delete operations count towards your document delete costs" ([ttl](https://firebase.google.com/docs/firestore/ttl)). **So what:** retention is priced as deletes — cheap at this scale (a few thousand entries/day), but not free, and the deletes are billed to the same project.
- "Deleting a document through TTL does not delete subcollections under that document", and deletion is not transactional or ordered ([ttl#ttl_deletion](https://firebase.google.com/docs/firestore/ttl#ttl_deletion)). **So what:** an audit entry must be a flat document with no subcollection, or its TTL will leave orphans.
- Limits: one TTL field per collection group, and up to 1,000 field-level configurations ([ttl#limits_and_constraints](https://firebase.google.com/docs/firestore/ttl#limits_and_constraints)). **So what:** one field per audit collection group is plenty — TTL is a single `expiresAt` field.
- **TTL deletes are not audit logged**: "Individual writes from import, bulk delete operations and TTL are not audit logged" ([Firestore audit logging](https://cloud.google.com/firestore/docs/audit-logging)). **So what:** retention by TTL is itself invisible in Cloud Audit Logs — so an attacker cannot hide a deletion behind TTL, but neither can you prove when an entry expired; the retention policy belongs in the written policy document, not in the log.
- Availability: TTL is configured per collection group on a Firestore native database; in the current docs the field-type rules differ by "Standard" vs "Enterprise" edition ([ttl](https://firebase.google.com/docs/firestore/ttl)). **So what:** on this project's standard native database the field must be a timestamp — check that before writing a policy, because an unset field disables expiry for that document.

## 5. Alternatives and adjuncts, and their exact limits

### 5.1 Cloud Functions / Cloud Run triggered writes

- Firestore triggers receive `event.data.before` and `event.data.after` snapshots ([functions/firestore-events#event_data](https://firebase.google.com/docs/functions/firestore-events#event_data)). **So what:** a trigger can write an entry containing the actual before/after delta without the browser ever being asked to describe it.
- The `…WithAuthContext` trigger variants expose "user authentication information about the principal that triggered the event", read as `event.authType` / `event.authId` ([functions/firestore-events#auth-context](https://firebase.google.com/docs/functions/firestore-events#auth-context)). The fields come from the CloudEvents Auth Context extension, whose `authid` is "a unique identifier of the principal that triggered the occurrence" and which is "purely informational and is not intended to secure CloudEvents" ([CloudEvents Auth Context](https://github.com/cloudevents/spec/blob/main/cloudevents/extensions/authcontext.md)). **So what:** this is the one way to attribute a *direct-to-Firestore* write to a Firebase Auth UID on the server side — it is the actor, not the claim. Note the spec's own warning: it is informational, so treat it as evidence produced by the platform, and still pin the actor in the document (`actorUid == request.auth.uid`) as a second, rules-enforced copy.
- Delivery is "at-least-once execution of an event-driven function for each event emitted by an event source" ([functions/retries](https://firebase.google.com/docs/functions/retries)). **So what:** the same write can produce two audit entries; the trigger must dedupe on the Firestore event's stable id (or a deterministic entry id), or the log lies about how many times something happened.
- Writing to the document that triggered the function risks an infinite loop, and the docs warn explicitly ([functions/firestore-events](https://firebase.google.com/docs/functions/firestore-events)). **So what:** audit entries must live in a collection no trigger watches for audit-writes — the natural design anyway, since the audit collection is `allow write: if false`.
- A Cloud Run request is only possible online, and this app's attendance taps are offline-first ([enable-offline](https://firebase.google.com/docs/firestore/manage-data/enable-offline)). **So what:** the existing API is the right writer for privileged actions (sign-in, driver/operator management, role changes, exports — all online), but it cannot be the writer for a bus in a dead zone.

### 5.2 Firebase App Check

- App Check obtains "an attestation of the app or device's authenticity" and only accepts requests carrying a valid App Check token ([App Check](https://firebase.google.com/docs/app-check)). **So what:** it proves the request came from a real build of the app, not that the user is honest.
- "It prevents some, but not all, abuse vectors directed towards your backends. Using App Check does not guarantee the elimination of all abuse" ([App Check](https://firebase.google.com/docs/app-check)). **So what:** with a valid token and a signed-in driver, the browser can still write any field the rules permit — App Check does not make audit content unforgeable.
- Enforcement exists for Cloud Firestore ([App Check enforcement](https://firebase.google.com/docs/app-check/enable-enforcement)). **So what:** worth enabling to raise the cost of scripted abuse, but it is orthogonal to the audit-trust requirement and should not be presented to the school as a control on log integrity.

### 5.3 Cloud Audit Logs (the Google-side trail)

**Short answer to "is the Firestore data plane covered?": yes at RPC level, no at document level.**

- Firestore emits Admin Activity and Data Access audit logs; `google.firestore.v1.Firestore.Commit` and `BatchWrite` are listed as **DATA_WRITE** data-access methods, and `RunQuery`/`Listen`/`BatchGetDocuments` as DATA_READ ([Firestore audit logging](https://cloud.google.com/firestore/docs/audit-logging)). **So what:** Google already logs that *a* commit happened against the database — at RPC granularity, not "director X moved student Y from bus A to bus B".
- Data Access audit logs are **disabled by default** for everything except BigQuery, and enabling them "might result in your Google Cloud project being charged for additional log usage"; Admin Activity logs "are always written; you can't configure, exclude, or disable them" ([Cloud Audit Logs](https://cloud.google.com/logging/docs/audit)). **So what:** the useful half (data writes) is opt-in and billable; the free half (admin changes) does not cover roster/attendance.
- "Log entries written by Cloud Audit Logs are immutable" ([Cloud Audit Logs](https://cloud.google.com/logging/docs/audit)). **So what:** this is a real tamper-evidence primitive, but only for what it records — and it records RPCs, not business actions.
- Retention: 400 days in `_Required` (not configurable), 30 days by default in `_Default` for a project, configurable between 1 and 3,650 days; retention costs apply beyond the default ([Logging quotas and limits](https://cloud.google.com/logging/quotas#logs_retention_periods)). **So what:** with defaults, a data-access trail exists for 30 days — too short for a school year unless retention is raised (and paid for).
- Not logged: "Individual writes from import, bulk delete operations and TTL" ([Firestore audit logging](https://cloud.google.com/firestore/docs/audit-logging)). **So what:** the platform trail has holes exactly where bulk operations and retention happen.
- **⚠ uncertain:** the docs list Commit/BatchWrite at method granularity and do not document the per-document payload of those entries; I could not confirm that a Firestore data-access entry lets you reconstruct which document fields changed, or that it carries a Firebase Auth UID as `principalEmail`. Do not design the director-facing log on that assumption.

### 5.4 BigQuery export of Cloud Logging

- Logging sinks stream entries into BigQuery in small batches, typically visible "within one minute", with schema-mismatch rows diverted to an `export_errors` table ([Logging to BigQuery](https://cloud.google.com/logging/docs/export/bigquery)). **So what:** near-real-time querying, with a documented loss path when a new field breaks the schema.
- The same page now recommends storing entries in a log bucket, upgrading it to Observability Analytics and querying a linked dataset, rather than the legacy BigQuery sink ([Logging to BigQuery](https://cloud.google.com/logging/docs/export/bigquery)). **So what:** if BigQuery is wanted, the linked-dataset route is the current recommendation; either way it is an *analysis* store, not the system of record.
- BigQuery tables are ordinary mutable tables — standard SQL `UPDATE`/`DELETE` are supported DML ([BigQuery DML](https://cloud.google.com/bigquery/docs/reference/standard-sql/dml-syntax)). **So what:** exporting to BigQuery does not make a log append-only; anyone with data-editor rights can rewrite rows. It adds durability and query power, not tamper-evidence.

## 6. Tamper-evidence: hash chains, what breaks, and Firestore's limits

### 6.1 Is there official guidance?

- **No.** I found no Firebase or Google Cloud documentation prescribing a hash-chained audit log on Firestore; none of the pages I read on rules, triggers, TTL or quota limits describes a ledger, chain or seal pattern. **So what:** this is a pattern you own and must document yourself; there is no "supported configuration" to point a school at, and no vendor guarantee behind it.
- What *is* officially supported is tamper-evidence at the storage layer: Cloud Audit Logs entries are immutable ([Cloud Audit Logs](https://cloud.google.com/logging/docs/audit)); a log bucket can be locked so it cannot be updated or deleted, irreversibly ([Logging buckets — lock](https://cloud.google.com/logging/docs/buckets#locking-logs-buckets)); and a Cloud Storage bucket can carry a retention policy under which objects "can only be deleted or replaced once their age is greater than the retention period", with the policy lock being irreversible ([Bucket Lock](https://cloud.google.com/storage/docs/bucket-lock#retention-policy), [Bucket Lock — policy locks](https://cloud.google.com/storage/docs/bucket-lock#policy-locks)). **So what:** the cheap, supported tamper-evidence is "seal the digest somewhere immutable", not "make Firestore immutable".
- The general pattern has a primary spec: Certificate Transparency (RFC 9162) defines an append-only Merkle tree with signed tree heads, inclusion proofs and consistency proofs, and states that "violation of the append-only property… can be detected by multiple clients comparing their instances of the STHs" ([RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.txt)). Trillian is Google's open-source implementation of verifiable logs ([Trillian](https://github.com/google/trillian)). **So what:** if the chain is to be meaningful, the head (STH equivalent) must be published/compared somewhere the writer cannot rewrite — that is exactly what a locked bucket or a second party gives you. A chain that only exists inside the same Firestore database is decoration: whoever can edit an entry can also recompute every hash after it.
- NIST's log-management guidance (SP 800-92) treats log protection, retention and review as part of a managed process ([NIST SP 800-92](https://csrc.nist.gov/pubs/sp/800/92/final)). **So what:** the school-facing part is not just storage — someone has to review and retain; that belongs in the policy even if the code is small.

### 6.2 What breaks when you chain inside Firestore

- **A single chain head is a hot document.** Every append reads the head and writes the next one, in a transaction; Firestore resolves contention by delaying or failing one operation, and after finite retries returns "ABORTED: Too much contention on these documents. Please try again." ([transaction contention](https://firebase.google.com/docs/firestore/transaction-data-contention)). Mobile/web SDKs use optimistic concurrency, which is what produces those retries ([transaction contention](https://firebase.google.com/docs/firestore/transaction-data-contention)). **So what:** one global head per school serialises all audit writes through one document; with 40 buses boarding at once, that is a contention hotspot, and failed appends are lost events unless the writer retries forever.
- **Per-document write rate.** The current docs do not publish a hard per-document write limit: they say "the exact maximum rate that an app can update a single document depends highly on the workload" and that at high rates the database "will start to encounter contention, higher latency, or other errors" ([best practices — updates to a single document](https://firebase.google.com/docs/firestore/best-practices#updates_to_a_single_document)). **⚠ uncertain:** the long-standing "≈1 write/second per document" figure is **not** stated on today's quotas or best-practices pages — I could not find it in the current docs. Treat ~1/s as a planning heuristic, not a documented guarantee.
- **Sequential timestamps cap a collection at 500 writes/s.** "If a collection contains documents with sequential indexed values, Firestore limits the write rate to 500 writes per second"; the official fix is a shard field (500 × n) plus aggregated queries ([Sharded timestamps](https://firebase.google.com/docs/firestore/solutions/shard-timestamp)). **So what:** an append-only audit collection indexed by a monotonic `at` field is the textbook anti-pattern above 500 writes/s — far above a school's load, so not the binding constraint here, but it is the documented ceiling and it is why sharding exists.
- **Size and per-commit limits.** A document is at most 1 MiB and a field value at most 1 MiB − 89 bytes; an API request is at most 10 MiB; a transaction has a 270-second time limit with 60-second idle expiry, and at most 500 field transformations per commit/transaction ([Firestore quotas](https://firebase.google.com/docs/firestore/quotas#writes_and_transactions)). **⚠ uncertain:** the often-quoted "500 writes per transaction" cap is **not** in the current quotas table; the docs only warn that "a batched write with hundreds of documents might… exceed the limit on transaction size" ([transactions](https://firebase.google.com/docs/firestore/manage-data/transactions)). Do not build around 500 as if it were documented.
- **Optimistic retries are the failure mode, not the write limit.** Because each append is a read-modify-write of the head, contention shows up as ABORTED + retry, and the retry loop is the client's ([transaction contention](https://firebase.google.com/docs/firestore/transaction-data-contention)). **So what:** a chain designed as one document per event will produce occasional unexplained gaps under load — the worst failure mode for an audit log.
- **The scalable shape is a sealed batch, not a per-event link.** Write entries as independent, immutable documents (no shared head), then have a single-writer job (Cloud Scheduler → Cloud Run/Function) compute a Merkle root or rolling hash over each batch and write a `seal` document plus publish the root outside Firestore (§6.1). That converts N contended writes into N independent creates and one uncontended seal. **⚠ uncertain (design inference):** this is my synthesis of RFC 9162's batch/STH model with Firestore's contention behaviour, not a documented Firestore recipe.
- **Truncation is the gap a chain does not close.** A chain detects edits, not deletion of the tail; RFC 9162's answer is that the head is signed and compared by others ([RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.txt)). **So what:** the seal document inside Firestore proves nothing to a Firestore admin; the root must be copied to a locked GCS object (immutable for the retention period) or a locked log bucket, and ideally given to the director as an exportable receipt.
- **Rules cannot verify the chain.** Rules can hash one string with `sha256` ([rules.hashing](https://firebase.google.com/docs/reference/rules/rules.hashing)) but cannot walk N links under the 10/20 access-call cap ([rules-structure#security_rule_limits](https://firebase.google.com/docs/firestore/security/rules-structure#security_rule_limits)). **So what:** verification is an API/CLI job and a director-facing "verify" button that calls it — never a rules guarantee.

## 7. Log injection and log forging in this stack

- OWASP's canonical injection example: a value containing `%0a%0aINFO:+User+logged+out%3dbadguy` produces an extra line that "looks like it came from a completely different user" ([OWASP Log Injection](https://owasp.org/www-community/attacks/Log_Injection)). **So what:** any string that reaches an audit entry (a student name, a bus label, an operator's typed reason) is an injection vector if the entry is ever rendered as text or exported to a line-oriented format.
- OWASP's control: "Perform sanitization on all event data to prevent log injection attacks e.g. carriage return (CR), line feed (LF) and delimiter characters", and encode data for the output format ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). **So what:** with Firestore, the document is already structured (no line format) — the residual risk moves to the React render, the CSV export and any `console.log`. Render as text (React's default escaping), never as HTML, and escape on CSV export.
- Rules can do the first pass: reject CR/LF and non-allowlisted characters with `matches()` (whole-string RE2) and cap length with `size()` ([rules.String#matches](https://firebase.google.com/docs/reference/rules/rules.String#matches), [rules.String#size](https://firebase.google.com/docs/reference/rules/rules.String#size)). **So what:** a client-write path can at least guarantee the *shape* of a text field, even though it cannot verify the truth of its content.
- Oversized fields: Firestore caps a document at 1 MiB and a field value at 1 MiB − 89 bytes ([Firestore quotas](https://firebase.google.com/docs/firestore/quotas#collections_documents_and_fields)). **So what:** an unbounded "details"/"payload" field can make an entry unwritable at exactly the moment it matters; cap text fields at a few hundred bytes by rule.
- Unicode: bidirectional text spoofing is a documented Unicode security issue — an RLO/embedding can make a rendered string read as something else ([UTR #36 §2.5](https://www.unicode.org/reports/tr36/tr36-15.html)). This is directly relevant: the UI is Arabic/English and therefore already mixes RTL and LTR runs. **So what:** a forged driver name or note can be made to display as a different actor or action in a log row. Reject bidi control characters (`U+202A–U+202E`, `U+2066–U+2069`) and other format controls in free-text fields; keep free text out of the entry entirely where possible.
- Note on currency of that source: UTR #36 is stabilized and "has not been maintained since 2014"; it defers to UTS #39 for current mechanisms ([UTR #36 index](https://www.unicode.org/reports/tr36/)). **So what:** cite it for the risk, not for the mitigation list; the mitigation here is simply "no free text / strip controls".

## 8. Privacy: what must not be in the log

- FERPA defines an "education record" as records that are "(1) Directly related to a student; and (2) Maintained by an educational agency or institution or by a party acting for the agency" ([34 CFR §99.3](https://www.ecfr.gov/current/title-34/subtitle-A/part-99/subpart-A/section-99.3)). **So what:** an audit entry that names a student and records that they were absent is itself an education record — the log inherits FERPA's protections, and a leak of the log is a leak of education records.
- The same section defines PII to include the student's name, parent/family names, address, "a personal identifier, such as the student's social security number, student number, or biometric record", and "other indirect identifiers, such as the student's date of birth, place of birth, and mother's maiden name", plus "other information that, alone or in combination, is linked or linkable to a specific student" ([34 CFR §99.3](https://www.ecfr.gov/current/title-34/subtitle-A/part-99/subpart-A/section-99.3)). **So what:** a "student number" is explicitly PII, so even an opaque school ID is protected data; the log should carry the *internal document reference* (an opaque Firestore ID) and a display name resolved at read time from the roster the director can already read.
- FERPA separately requires a record of access: an institution "must maintain a record of each request for access to and each disclosure of personally identifiable information from the education records of each student", including "the parties who have requested or received" it and "the legitimate interests" they had — with an exception for internal school officials, the parent/student, consent, and directory information ([34 CFR §99.32](https://www.ecfr.gov/current/title-34/subtitle-A/part-99/subpart-D/section-99.32)). **So what:** there is a *legal* audit-log requirement here, but it is about disclosures to outsiders, not about the director's own reads. The "major behaviours" log and the FERPA disclosure record are two different logs with two different readerships; conflating them creates privacy exposure without adding compliance.
- GDPR Art. 30 requires a record of processing activities containing the purposes, "the categories of data subjects and of the categories of personal data", recipients, and "where possible, the envisaged time limits for erasure of the different categories of data" ([GDPR Art. 30](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32016R0679)). **So what:** if any EU/UK school is in scope, the audit log needs a written purpose and a stated erasure period; "keep everything forever" is the one answer that is definitely wrong under Art. 5(1)(e) storage limitation in the same text.
- OWASP's "data to exclude" list says the following "should usually not be recorded directly in the logs, but instead should be removed, masked, sanitized, hashed, or encrypted": session IDs, access tokens, "sensitive personal data and some forms of personally identifiable information (PII) e.g. health, government identifiers, vulnerable people", passwords, connection strings, keys, payment data, and "data of a higher security classification than the logging system is allowed to store" ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). **So what:** for a bus app the exclusions are concrete — no child's medical/health note, no home address, no guardian phone, no photo URL, no GPS trace, no auth code, and no Firebase ID token in an audit entry. Children are "vulnerable people" in the OWASP sense, which is an argument for maximising the exclusion rather than testing the line.
- OWASP also says to de-identify "direct and indirect identifiers where the individual's identity is not required, or the risk is considered too great" ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). **So what:** the entry needs *what happened and who did it*, not *who it happened to* in human-readable form — store the student's opaque ID, and let the director's UI join it to a name it is already allowed to read.
- **⚠ uncertain:** whether FERPA treats the audit log itself as a student education record in every case is a legal question, not something these regulations state explicitly; the safe reading (it is directly related to a student and maintained by the school) is the one to design to, and a lawyer should confirm for the school's jurisdiction.

## Verdict for this stack

**Recommendation.** Do not let the browser write the director-facing audit collection at all. Build the trail from two server-side sources into one append-only, director-read collection, then add a separate integrity layer:

1. **Privileged actions → the existing Hono API (Admin SDK).** Every `/v1` mutation that changes access or identity (driver create/code rotate, operator create/re-scope, sign-in success/failure, owner changes, exports) writes one audit entry in the same handler, before responding. This is the part that is already online and already trusted; it needs no new infrastructure.
2. **Direct roster/attendance writes → a Firestore trigger (gen 2, `onDocumentWrittenWithAuthContext`) writing the entry via the Admin SDK.** This is the only way to cover an offline tap, because the write reaches Firestore only when the device reconnects — and the trigger sees it then, with `before`/`after` and the platform's auth context. Dedupe on the event id.
3. **Store:** `schools/{schoolId}/audit/{entryId}` — director-read, `allow write: if false` (already the shape in this repo), flat documents (no subcollections, so TTL works), schema-fixed, text-capped, no names.
4. **Integrity:** entries are independent, immutable documents; a daily (or hourly) single-writer job computes a Merkle root over the batch, writes a `seal` doc, and copies the root to a **locked** Cloud Storage object (retention ≥ the school's retention period). Verification is an API endpoint/CLI that recomputes from the entries and compares to the sealed root. Without step 4, "tamper-evident" means "tamper-evident to a browser", which is the requirement already met by `allow write: if false`.
5. **Retention:** TTL on an `expiresAt` timestamp field, set to the school's documented period; remember TTL deletes are not in Cloud Audit Logs and take up to 24 h.
6. **Optional adjunct:** enable Firestore Data Access audit logs (billable, 30-day default retention) for a system-level second trail, and treat it as incident-response evidence, not as the director's log.

### Tradeoffs

| Option | What it buys | What it costs / breaks | Verdict |
| --- | --- | --- | --- |
| **A. Browser writes entries to an append-only collection** | Works offline, zero new infra, one rules change | Content is entirely client-chosen: any driver can write a false action, back-date it unless `request.time` is pinned, and omit entries. Fails the "not forgeable by the audited party" requirement | **No** for the director's log. Acceptable only as a clearly-labelled "inbox of claims" that the server later re-derives |
| **B. API-only audit (Admin SDK)** | Trustworthy actor (verified token), simple, same-origin `/v1`, no new service | Blind to every direct-to-Firestore write — i.e. all attendance, the app's core event; also fails when the device is offline | **Yes**, for privileged/identity actions |
| **C. Firestore trigger (gen 2, auth context) → Admin SDK entry** | Covers offline-synced writes; sees before/after; attributes the UID; no browser trust | At-least-once duplicates; trigger latency; no per-tap granularity if the client's queued edits collapse to the committed state; a silent deploy failure loses events unless monitored; per-write cost | **Yes**, for roster/attendance — the only option that covers offline |
| **D. C/B + hash chain + sealed root in a locked GCS object** | Detects edits by anyone holding Admin SDK/IAM, not just browsers; gives the director a verifiable receipt | Extra job + canonicalisation + verifier; lock is irreversible; wrong chain shape (one head) creates contention and gaps | **Yes**, as the integrity layer; seal per batch, never per event |
| **E. Cloud Audit Logs (+ BigQuery export)** | Immutable entries, admin-activity always on, easy BigQuery querying | Data Access off by default and billable; 30-day default retention; RPC granularity, no document-level payload confirmed; excludes import/bulk-delete/TTL; not director-readable | **Optional** adjunct for incident response, not the audit trail |
| **F. TTL for retention** | Cheap, no code, per collection group | Deletes cost money, up to 24 h late, not audit-logged, leaves subcollections | **Yes**, with a documented retention period |
| **G. App Check** | Raises the cost of scripted abuse of the client SDK | Attests app/device, not the user; "prevents some, but not all"; does nothing for server writes | **Enable anyway**, but it is not part of the audit-trust argument |

### What rules cannot do

- Cannot limit **write rate** or event frequency (no loops, no cross-request state).
- Cannot impose **ordering** between entries; each request is evaluated alone.
- Cannot verify a **hash chain** beyond a single 10/20-call window.
- Cannot tell whether a write was made **offline and replayed** on reconnect.
- Cannot force an audit entry to exist for a direct write — except via `getAfter()` inside a transaction/batch, and only at a fully specified path; it still cannot make the entry's content true.
- Cannot stop a client from **omitting** an entry, or from **squatting** on a client-chosen document ID in a create-only collection (⚠ inference from `create` semantics — so never derive audit IDs from client-visible sequences).
- Cannot make server timestamps **automatic**; only `request.time == field` checks make one field trustworthy.
- Cannot **strip** an offending field and accept the rest — the whole write is rejected.
- Cannot **hide a field** from a reader who may read the document.
- Cannot **filter** a query (rules are not filters), so they can't narrow what a director reads within the collection.
- Cannot bind a caller to a **particular app build** (that is App Check's job) or to a **particular person** behind a shared 6-digit driver code — identity is account-level, so non-repudiation is only as good as code handling.
- Cannot bind the **Admin SDK** at all: IAM and code review are the only controls on the writer that makes entries trustworthy.
- Cannot prove **semantic truth**: no rule can distinguish "driver tapped Boarded" from "driver's client posted BOARDED". That limit survives every option above; the audit log can prove *who wrote what, when, and that it was not edited afterwards* — not that the child actually boarded.

### Open questions to settle by test (not by more reading)

1. Whether the Firestore local queue sends every offline mutation to the backend or collapses repeated writes to one document (⚠ undocumented for this case) — this decides whether trigger-based auditing preserves per-tap history or only the final state.
2. Whether Firestore Data Access audit log entries for `Commit` carry document paths/field deltas and a Firebase Auth UID (⚠ unconfirmed) — do not promise either to the school.
3. The practical per-document write rate for a chain head on the project's actual edition/region (⚠ no documented number) — load-test before choosing per-event chaining over batch sealing.
